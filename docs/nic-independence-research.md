# Kernel-side PnP boots only reflected NIC packages

*Research, written 2026-10-11 after the NIC test results in [image.md](image.md#results-2026-10-11-on-golden-v1-built-on-an-e1000e): web sources (iPXE forum and GitHub discussions, Microsoft docs, OSR, the virt-v2v and Rapr sources, QEMU and Proxmox sources, driver INFs) checked against the lab's recorded findings. Untracked working notes, like [winpe-iscsi-research.md](winpe-iscsi-research.md): fold what matters into image.md once the next tests have run. Evidence grades in brackets: documented, working code, first-hand report, lab, local check, inferred. The raw notes (seven files, about 470 KB, with a URL on every claim) are in `C:\Users\clanc\.claude\projects\c--Programming-Git-windows-scsi-boot\research-notes\Windows iSCSI boot on other NICs\`.*

The e1000e image boots a new e1000e machine because Windows Setup **reflected** the Intel package as a critical driver into the image's `SYSTEM` hive: it created `Services\e1iexpress` (with `BootFlags=1` from Intel's INF) and wrote the package's configuration under `SYSTEM\DriverDatabase`, so winload promotes the service to boot-start when it sees the iBFT and the kernel's own PnP configuration engine builds a devnode for the never-seen PCI instance from that in-memory database before any file system exists. virtio-net and vmxnet3 fail because DISM only **staged** their packages: payload in `FileRepository` and metadata in the separate `DRIVERS` hive, which the kernel cannot open until the boot volume it is looking for is already mounted. With no service nothing loads and the 0x7B is immediate; with the lab's hand-copied service the driver loads but finds no configuration for its device, and `msiscsi.sys` spends its boot-time retry budget before the kernel gives up a few minutes later. `BootFlags`, `Start=0` and `/Add-NetAdapter` cannot supply the missing configuration, which is why every variant short of reflection failed. The lab's next step, `DriverStoreOfflineAddDriverPackageW` with flags 0x180, is the right mechanism (0x180 = `ReplacePackage|Force`, where Force means "force offline reflection regardless of device class"), but the planned fallback of flags 1 means `SkipInstall` and would only stage the package again; the correct fallback is **0x140 (`InstallOnly|Force`)**. Ranked by evidence and effort, the routes to one image on many NICs are: force-reflect each NIC package into the image (Setup's own mechanism, scripts already written); one golden image per NIC family built by Setup (the only Microsoft-documented path, with a 2026 first-hand vmxnet3 precedent and none for virtio-net); a hand-written `DriverDatabase` reflection (production code exists for the storage class); pre-seeded devnodes from a specialisation boot (viable for virtio-net, whose instance ID is slot-based, but not for DSN-bearing e1000e/vmxnet3 or Intel physical NICs unless `HackFlags` disables serial numbers); a multi-NIC iBFT at build time (untested); per-client devnode cloning on the storage server; INF edits (the wrong layer); and iSCSI HBAs for physical boxes. The decisive diagnostics need no debugger: offline `SYSTEM`-hive checks the storage server can run on a mounted child, a `tcpdump` on the client's tap on the Proxmox node, and Kernel-PnP event 400 on the e1000e client that already boots.

## Winload promotes the service, the kernel configures the device, and both read only the SYSTEM hive

Three components consume the iBFT, and each needs something a staged package does not have. `winload.efi` contains the strings `iBFT`, `BootFlags` and `BootDriverFlags` (observed on a Windows 11 26200 machine [local check]), and Microsoft's NDIS engineer Jeffrey Tippet stated that the network-boot condition for promoting a service is "set iff IBFT is present" ([OSR, 2016](https://community.osr.com/t/network-boot-and-bootflags-how-does-windows-know/52391)) [documented, Microsoft staff]. Microsoft's INF reference defines `BootFlags` 0x1 (`CM_SERVICE_NETWORK_BOOT_LOAD`) as "the driver should be promoted if booting from the network" and, from build 25398, offers a first-class `BootFlags=` directive plus the `SPSVCINST_NOCLOBBER_BOOTFLAGS` (0x40000) AddService flag ([INF AddService directive](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/inf-addservice-directive)) [documented]. Winload reads `Services\<svc>` keys from the `SYSTEM` hive, which it loads itself before the kernel runs ([Project Zero, registry hives](https://projectzero.google/2024/10/the-windows-registry-adventure-4-hives.html)) [reverse-engineered]. So promotion is **per service, not per device**: `e1iexpress` with `Start=3`, `BootFlags=1` and an iBFT present is loaded by winload whatever the NIC's MAC or instance ID. `netkvm` and `vmxnet3ndis6` have no service key at all in the image (DISM staging creates none for Net-class packages, as the lab's `setupapi.offline.log` and `test-client.ps1`'s `service netkvm: none` show [lab]), so there is nothing to promote. Both vendor INFs confirm why: NetKVM's service section has `StartType=3`, `LoadOrderGroup=NDIS` and no `BootFlags` ([netkvm-base.txt](https://raw.githubusercontent.com/virtio-win/kvm-guest-drivers-windows/master/NetKVM/netkvm-base.txt)), and vmxnet3 1.9.21.0's section is `StartType=3`, `ServiceBinary=%12%\vmxnet3.sys`, `LoadOrderGroup=NDIS` with zero `BootFlags` [local check]. Signing is not the blocker: `netkvm.sys` and `vmxnet3.sys` 1.9.21.0 carry embedded "Microsoft Windows Hardware Compatibility Publisher" signatures [local check], and with Secure Boot off the policy table permits them ([Driver Signing Policy](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/kernel-mode-code-signing-policy--windows-vista-and-later-)) [documented].

The second component is the kernel's boot-time device configuration. Windows 7 used the `CriticalDeviceDatabase` for this ([NTDebugging, CDDB tip](https://learn.microsoft.com/en-us/archive/blogs/ntdebugging/critical-device-database-tip)) [documented, Win7]; since Windows 8 the key is gone and "replaced by the in-registry Driver Database" ([OSR NTDEV](https://community.osr.com/t/hklm-system-driverdatabase-driverpackages-bus-driver-inf-not-properly-configured/52214)) [first-hand]. The strongest evidence that the kernel really installs a never-seen device from `SYSTEM\DriverDatabase` is production code: libguestfs/virt-v2v makes Windows 8 through 11 guests boot from a virtio disk they have never seen by writing only `Services\<drv>` plus five `DriverDatabase` keys, and the 2017 commit that added the `Version` blob explains that "in w10/w2k16 was changed the behavior of Windows-Kernel-Pnp where driver installation can now be done from the kernel", with the failure signature `Selecting driver failed(0xe0000228)` → `Installing NULL driver` → 0x7B when the entries were incomplete ([libguestfs list, 2017](https://lists.libguestfs.org/archives/list/guestfs@lists.libguestfs.org/thread/WK53DG74P7A3EA7XAJMDBICLS7FT3T6E/); [inject_virtio_win.ml](https://github.com/libguestfs/libguestfs-common/blob/master/mlcustomize/inject_virtio_win.ml)) [working code]. An OSR Server 2012 R2 case shows the mirror image: a package installed online lacked `Configurations`, `Descriptors` and `Strings` under `SYSTEM\DriverDatabase\DriverPackages\<pkg>`, the devnode sat in `CM_PROB_NOT_CONFIGURED` and the SAN LUN died with 0x7B until those three subkeys were imported ([OSR NTDEV](https://community.osr.com/t/hklm-system-driverdatabase-driverpackages-bus-driver-inf-not-properly-configured/52214)) [first-hand]. The kernel logs its own choice as `Microsoft-Windows-Kernel-PnP/Configuration` event 400 with Driver Name, Driver Rank, Matching Device Id and "Device Updated" fields ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/1200807/what-does-microsoft-windows-kernel-pnp-configurati)) [documented event], and a 2019 ntoskrnl symbol dump contains the matching machinery (`PpInitializeBootDDB`, `PiDevCfgConfigureDevice`, `PiDevCfgVerifyService`, `PiDevCfgMakeServiceBootStart`, `PnpBootDeviceWait`) ([JEB symbol dump](https://lise.pnfsoftware.com/winpdb/2C5423AE810E58D725A98CB83193CB9180FECB7509367EAAA08F2FC2D89F551D-ntoskrnl.html)) [reverse-engineered, names only]. What the kernel cannot do at that point is copy a `.sys` into `System32\drivers` or create a `Services` key, because the volume holding them is the one it is trying to reach [inferred]. That is exactly the split Microsoft's own definition of reflection draws: "Boot-critical drivers are reflected ... copying the driver files to a destination location and creating the service", while other drivers "are staged ... added to the driver store" ([Add and Remove Drivers Offline, Win7](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-7/dd744355(v=ws.10)); [Device Drivers and Deployment Overview, Win8.1](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-8.1-and-8/hh825697(v=win.10))) [documented]. Staging writes its metadata to the `DRIVERS` hive ([BSI, Device Setup Manager analysis, p. 38](https://www.bsi.bund.de/SharedDocs/Downloads/EN/BSI/Cyber-Security/SiSyPHuS/AP3d/Workpackage3d_Analysis_Device_Setup_Manager.pdf?__blob=publicationFile&v=2)) [reverse-engineered], which is "loaded by the kernel on demand" from `config\DRIVERS` on the boot volume ([Project Zero](https://projectzero.google/2024/10/the-windows-registry-adventure-4-hives.html)) [reverse-engineered]. Microsoft's current wording, "the driver package is added to the driver store. When the image boots, Plug and Play (PnP) runs and associates the driver packages" ([Add and Remove Driver packages to an Offline Windows Image](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/add-and-remove-drivers-to-an-offline-windows-image)) [documented], describes a user-mode association that never happens on a boot NIC.

The third component is `msiscsi.sys` (service `iScsiPrt`), which also contains `iBFT` and a set of boot-time wait parameters, `WaitForNetworkAtBoot`, `DelayForNetworkAtBoot`, `NetworkReadyRetryCount`, `PortalRetryCount` and `BootConnectionPoolSize`, under the registry path `iscsiprt\parameters` [local check, strings in msiscsi.sys 10.0.26100.9444]; `tcpip.sys` and `ndis.sys` contain no iBFT reference [local check], so the initiator driver, not TCP/IP, applies the NIC record's address and logs in once an NDIS adapter exists [inferred]. This explains the lab's two latencies. With no boot-started NIC service, nothing network-related exists when the boot-device wait runs and the bugcheck is immediate; with a copied `Services\netkvm` carrying `BootFlags=1`, winload loads the driver, PnP builds a devnode but cannot configure it (Microsoft: "If a device's drivers are not all boot-start drivers, the PnP manager creates a device node for the device but does not start the device yet", [Specifying Driver Load Order](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/specifying-driver-load-order) [documented]), no `\Device\{GUID}` is exported for TCP/IP, and `msiscsi.sys` runs through its retry budget before the kernel declares 0x7B [inferred from the verified parameter names; defaults undocumented]. The documented initiator timers are the full-feature-phase ones, `MaxRequestHoldTime` 60 s, `TCPConnectTime` 15 s, `DelayBetweenReconnect` 1 s, `MaxConnectionRetries` -1, `NetworkReadyRetryCount` 10 ([iSCSI initiator timers quick reference](https://learn.microsoft.com/en-us/archive/blogs/san/microsoft-iscsi-software-initiator-and-isns-server-timers-quick-reference)) [documented, 2008]. This is the same picture Cyberus drew for Windows 7 on QEMU, where with the in-box e1000 driver loaded "the driver has to be initialized and configured as well" and Windows "only does this for devices it treats as boot-critical" ([Cyberus, Windows on iSCSI part 2](https://www.cyberus-technology.de/post/windows-on-iscsi---part-2-3)) [first-hand, Win7]. The delayed 0x7B therefore proves the driver loaded, not that the NIC ever transmitted; only a tap capture settles that.

One link in the chain remains undocumented and matters for the plan: how the kernel-configured new instance gets its `NetCfgInstanceId` and TCP/IP binding. Bindings are persisted in `Services\Tcpip\Linkage\Bind` as `\Device\{NetCfgInstanceId}` entries plus the adapter's `Class\{4D36E972-...}\00NN\Linkage\Export`, and Microsoft says these are system-generated ([Linkage subkeys, WS2003](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2003/cc759227(v=ws.10))) [documented]. `/Add-NetAdapter` is the offline tool that writes them: Setup's own log shows it resolving `ms_tcpip` and `ms_tcpip6` "to offline driver IDs" and then "create[ing] the network interface in the offline store" ([iPXE forum 22696](https://forum.ipxe.org/showthread.php?tid=22696); [Microsoft Q&A 337717](https://learn.microsoft.com/en-us/answers/questions/337717/installation-of-hyper-v-2019-on-iscsi-via-bcm5720)) [first-hand logs]. The lab's e1000e client with a new MAC booted without a fresh `/Add-NetAdapter`, so either the kernel reused the adapter object Setup created for the build VM's instance, or it minted a GUID (`PiDevCfgResolveVariableGenerateGuid` exists in the symbol dump [reverse-engineered, name only]) and NDIS bound TCP/IP regardless. Reading `Get-NetAdapter | select InterfaceGuid` on the booted e1000e client and comparing it with `Tcpip\Linkage\Bind` in the golden image's offline hive decides this, and it decides whether approach 1 below needs `/Add-NetAdapter` at all.

## The notes correct six things the lab believes or plans

**The fallback flags value is wrong.** `image/winpe/critical.ps1` loops `foreach ($flags in 0x180, 1)`. The only public source with flag enums for `drvstore.dll`, Rapr's `NativeDriverStore.cs`, defines `DriverStoreOfflineAddDriverPackageFlags` as `SkipInstall = 0x1` ("Add the package to the driver store but skip the installation"), `Inbox = 0x2`, `F6 = 0x4`, `SkipExternalFilePresenceCheck = 0x8`, `NoTempCopy = 0x10`, `UseHardLinks = 0x20`, `InstallOnly = 0x40` ("Only install (reflect) a driver package that is already in the driver store"), `ReplacePackage = 0x80` ("Replace the driver package if it is already present in the driver store"), `Force = 0x100` ("Force offline reflection regardless of device class when importing to the driver store") and `BaseVersion = 0x200` ([NativeDriverStore.cs](https://raw.githubusercontent.com/lostindark/DriverStoreExplorer/master/Rapr/Utils/NativeDriverStore.cs)) [community-derived enum, not a Microsoft header]. So **0x180 = ReplacePackage|Force is exactly what the lab wants**, consistent with the lab's own reading of `winsetup.dll`, and **flags 1 is the opposite of reflecting**. The sensible fallback for a package that is already staged is **0x140 = InstallOnly|Force**; whether `DriverPackageInfPath` must then name the image's own `FileRepository` copy rather than WinPE's is unknown, so try both paths. The P/Invoke in both lab scripts matches Rapr's signature (`infPath, flags, IntPtr reserved, ushort arch, string locale, StringBuilder dest, ref cch, targetSystemRoot, targetSystemDrive`), Rapr passes `IntPtr.Zero`/`null` for the undocumented `Reserved`/`LocaleName`, reads the architecture (9 = AMD64) from the offline database via `DriverStoreGetObjectPropertyW(..., DEVPKEY_DriverDatabase_ProcessorArchitecture {8163eb00-142c-4f7a-94e1-a274cc47dbba}, pid 3)`, and treats a non-zero return as a Win32 error code ([NativeDriverStore.cs](https://raw.githubusercontent.com/lostindark/DriverStoreExplorer/master/Rapr/Utils/NativeDriverStore.cs)) [working code for the open/enumerate/offline-add paths; Rapr never reflects offline itself]. A handle-based alternative exists if the one-shot call refuses: `DriverStoreOpenW(L"<vol>\Windows", L"<vol>\", 0, NULL)` → `DriverStoreImportW` → `DriverStoreReflectCriticalW(h, <FileRepository INF path>, Force 0x1 | Configurations 0x2, NULL)` → `DriverStorePublishW` → `DriverStoreClose`, where `DriverStoreReflectCriticalFlags.Force` is commented "Force reflection of non-boot critical driver packages" ([NativeDriverStore.cs](https://raw.githubusercontent.com/lostindark/DriverStoreExplorer/master/Rapr/Utils/NativeDriverStore.cs)) [declared in working code, argument conventions untested publicly]. The same DLL lets the scripts verify their own effect: `DriverStoreGetObjectPropertyW` with object type `DriverPackage` (2) and `DEVPKEY_DriverPackage_BootCritical` ({8163eb01-142c-4f7a-94e1-a274cc47dbba}, pid 16, BOOLEAN) or with `DeviceSetupClass` (6) and `DEVPKEY_DeviceClass_BootCritical` ({6a3433f4-5626-40e8-a9b9-dbd9ecd2884b}, pid 3) ([DeviceHelper.cs](https://raw.githubusercontent.com/lostindark/DriverStoreExplorer/master/Rapr/Utils/DeviceHelper.cs)) [working code]. Rapr's resolution order, version-info `FORCE_BOOT_CRITICAL`/`FORCE_NOT_BOOT_CRITICAL` flags first, then the class property, then false, is also the answer to why DISM reports `BootCritical=False` for Net-class packages: boot-criticality is a **class** property, and `StartType`/`BootFlags` play no part in it [working code + inferred]. Note that `docs/image.md` and `PLAN.md` say only `/Add-NetAdapter` can be run by hand; the drvstore path is now runnable too, as both lab scripts show.

**`/Add-NetAdapter` alone does not help, and the only public claim that it did was retracted.** The lab's results table already shows this, and `docs/image.md`'s reading, "`/Add-NetAdapter` alone creates the NIC and its TCP/IP binding, but no service", is consistent with the logs (`PNP device has driver service: <svc>` is read from the WinPE host adapter, not created). The widely quoted recipe in iPXE discussion #1544 (run `/Add-NetAdapter` from WinPE, copy the WinPE `Interfaces\{guid}` key, fix `NetCfgInstanceId`) was withdrawn by its author the next day: "I was wrong in how I remembered how dism /add-netadapter works ... It does not help with missing BootFlags ... the drivers never fully got installed to the point of adding the service (despite dism /add-driver). I seem to remember that I hacked up qemu to put fake pci IDs to force the driver to install" ([ipxe #1544, comment 15040865](https://github.com/ipxe/ipxe/discussions/1544#discussioncomment-15040865)) [first-hand]. His "QEMU/virtio" success used QEMU's built-in iSCSI backend, so the guest saw an ordinary disk and Windows never ran an initiator through virtio-net ([ipxe #1544, comment 15020066](https://github.com/ipxe/ipxe/discussions/1544#discussioncomment-15020066)) [first-hand]. Two of the research notes also attribute a `0x80073b01` failure to the lab's own `/Add-NetAdapter` run; the repository records no such error and `docs/image.md` describes the run as succeeding, so disregard that attribution. The 2020 `0x80073b01` (= Win32 15105, which `Win32Exception` renders as "The resource loader cache doesn't have loaded MUI entry" [local check]) was Setup's own step on a 19041 WinPE against an 18363 target ([iPXE forum 22696](https://forum.ipxe.org/showthread.php?tid=22696)) [first-hand log]; the lab's 26100-on-26100 combination succeeded, which fits Setup's "iSCSI target boot support matrix" error text and the Server 2019 `0x800710dd` (`ERROR_INVALID_OPERATION`) case where 2016 and 1809 passed and 17763.737 failed ([Microsoft Q&A 337717](https://learn.microsoft.com/en-us/answers/questions/337717/installation-of-hyper-v-2019-on-iscsi-via-bcm5720)) [first-hand, unresolved].

**The e1000e success does show the kernel configuring a new device at boot, with one check outstanding.** `sysprep /generalize` without `PersistAllDeviceInstalls` "uninstalls these configured devices" ([Sysprep generalize](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/sysprep--generalize--a-windows-installation)) [documented], and QEMU's e1000e exposes a PCIe Device Serial Number computed from the MAC (`pcie_dev_ser_num_init(pci_dev, 0x140, e1000e_gen_dsn(macaddr))`, unconditionally, [qemu e1000e.c](https://gitlab.com/qemu-project/qemu/-/blob/master/hw/net/e1000e.c)) [working code], which Windows 10/11 prefers for instance identity ([PCIe DSN conflicts](https://learn.microsoft.com/en-us/windows-hardware/drivers/pci/device-serial-number-conflict-workaround)) [documented]. Either fact alone means the client's e1000e devnode did not pre-exist, so the kernel built it from the reflected package. Two caveats remain. Microsoft once shipped a Windows 7 hotfix so that a "replacement PCI Express device with a different serial number keeps the same device instance path ... if it is the same model in the same slot" ([Microsoft, 0x7B after replacing an iSCSI NIC](https://support.microsoft.com/en-us/servicing/os/windows/2017/01/0x0000007b-stop-error-when-you-replace-an-iscsi-or-pci-express-network-adapter-or-a-motherboard-with)) [documented, Win7], and nobody has stated whether current pci.sys does the same, so confirm by comparing the instance suffix of `Enum\PCI\VEN_8086&DEV_10D3&...\<instance>` in the golden image's offline hive (if sysprep left one) with the booted client's, and read the client's Kernel-PnP event 400 ("Device Updated: false" for a first configuration). And the kernel's "install" is a configuration from the in-memory hive, not a file copy or service creation; the lab's own wording in `docs/image.md` is right, but the automation must never expect a merely staged package to be rescued at boot.

**Device instance IDs are stable for virtio-net and unstable for the others, which inverts the lab's framing.** `docs/image.md` concludes that "every machine's NIC is a new device" and treats virtio-net's slot-based ID as a footnote. QEMU's vmxnet3 also writes a MAC-derived DSN (`fe`, `mac[3..5]`, `mac[0..2]`, `ff` at capability offset 0x100, [qemu vmxnet3.c](https://gitlab.com/qemu-project/qemu/-/blob/master/hw/net/vmxnet3.c)) [working code], while `virtio-pci.c` adds no serial-number capability ([qemu virtio-pci.c](https://gitlab.com/qemu-project/qemu/-/blob/master/hw/virtio/virtio-pci.c)) [working code, absence]. Proxmox places `net0` at bus 0 address 0x12, `net1` at 0x13 and so on from one table regardless of machine type ([qemu-server PCI.pm](https://github.com/proxmox/qemu-server/blob/master/src/PVE/QemuServer/PCI.pm)) [working code]. So a virtio-net devnode installed in the master at `net0` will match every client VM whose virtio NIC is `net0` on the same machine type, and a pre-seeded devnode approach (approach 4 below) is viable for virtio-net and for physical NICs without a unique DSN, but not for e1000e, vmxnet3 or DSN-bearing Intel cards, unless `HKLM\SYSTEM\CurrentControlSet\Control\PnP\Pci\HackFlags` bit 0x10000 (`PCI_SYS_HACK_DISABLE_EXPRESS_SERIAL_NUMBER_SUPPORT`) is set, after which "Device identification falls back to other methods, such as bus location" ([PCIe DSN conflicts](https://learn.microsoft.com/en-us/windows-hardware/drivers/pci/device-serial-number-conflict-workaround)) [documented, untested for this purpose].

**The "solved netkvm" thread is a pagefile thread about e1000e.** The 2020 virtio report (tid 22696) ends with "Solved." and a link to tid 19538. That thread is "Windows 10 iSCSI disk installation, second stage fails (error 0xc0000428)", a VMware Workstation 14 VM with an Intel e1000e (`e1i65x64.sys`), and its fix is clearing `PagingFiles` under `ControlSet001\Control\Session Manager\Memory Management` in the offline SYSTEM hive; it contains no occurrence of netkvm, virtio, BootFlags, DISM or DriverDatabase ([iPXE forum 19538, printthread](https://forum.ipxe.org/printthread.php?tid=19538)) [first-hand]. **No first-hand report of Windows 10 or 11 booting from iSCSI through virtio-net exists** in the iPXE forum, ipxe-devel, GitHub discussions, the virtio-win tracker or the Proxmox forum; the virtio-win project's only iSCSI items are a 2016 netkvm deadlock under iSCSI data traffic and a July 2026 fix for Server 2025 initiator connectivity, neither about boot ([issue #52](https://github.com/virtio-win/kvm-guest-drivers-windows/issues/52); [PR #1605](https://github.com/virtio-win/kvm-guest-drivers-windows/pull/1605)) [first-hand]. vmxnet3 is different: two 2026 reports boot Windows 11 24H2/25H2 from iSCSI through vmxnet3 on ESXi 8, one by Setup over iSCSI with vmxnet3 1.9.19.1 injected into WinPE and `StartType=3` left alone ([ipxe #1544, comment 16130320](https://github.com/ipxe/ipxe/discussions/1544#discussioncomment-16130320)), one by a local install with all drivers, `Start=0` on the NIC service, `MSiSCSI` and `iScsiPrt`, then a `dd` image onto the LUN booted on the same VM, build 26200.7705 ([ipxe #1544, comment 15657892](https://github.com/ipxe/ipxe/discussions/1544#discussioncomment-15657892)) [first-hand]. The pagefile finding itself recurs independently (Orakel von Delphi 2019, Moriarty 2020, dfh0522 2022, jakelmg 2023), so `docs/winpe-iscsi-research.md`'s "single-source and disputed" grading should be raised to "multiply reported, mechanism unknown"; the lab's e1000e boots with its current pagefile setting, so it is not today's blocker, but it is a confound to remember on physical clients.

**Windows Update can silently undo any of this.** A Realtek driver update renamed the service to `rt640x64` and dropped `BootFlags`, and on 25H2 builds between KB5067036 (2025-10-28) and 26200.7701 iSCSI boot broke independently of the NIC ([ipxe #1544, comment 15040865](https://github.com/ipxe/ipxe/discussions/1544#discussioncomment-15040865); [comment 15648882](https://github.com/ipxe/ipxe/discussions/1544#discussioncomment-15648882)) [first-hand]; Server 2025 (the same 26100 stream as LTSC 2024) needed KB5051987 for an NDIS poll-mode 0x7B ([borncity](https://borncity.com/win/2025/02/17/windows-server-2025-iscsi-boot-device-inaccessible-fixed/)) [secondary]. The lab's policy of updates only in new golden images is the right shape; test `--updates` builds separately and re-check `Services\<svc>\BootFlags` after each.

## Eight routes to one image on many NICs, ranked by evidence and effort

| Rank | Route | What it requires | Evidence | Effort |
|---|---|---|---|---|
| 1 | Force-reflect each NIC package into the image with `DriverStoreOfflineAddDriverPackageW` 0x180 (fallback 0x140), then `BootFlags=1`, then `/Add-NetAdapter` if the e1000e check says it is needed | Existing `critical`/`netadapter` variants with the flag fix and verification | This is what Setup did to net1ix64 in the lab's own log [lab]; flag semantics from Rapr [community enum]; kernel-at-boot configuration from a reflected package proven for storage [working code] and for Net by the e1000e result [lab] | Low |
| 2 | One golden image per NIC family, built by Setup on that NIC | `dl-build-1` with virtio or vmxnet3 `net0`; driver already in WinPE | Microsoft's only documented model ("same network adapter") [documented, 2008 R2]; vmxnet3 Setup install works on 25H2 [first-hand 2026]; virtio-net: no success report, one 2020 Setup failure | Low per family, linear ongoing |
| 3 | Hand-write the reflection into the offline SYSTEM hive (virt-v2v pattern) | Copy `.sys`, write `Services\<svc>`, `DriverDatabase` keys; take `Configurations` from a reflected copy | Production code for SCSIAdapter on Win8–11 [working code]; never done for Net class | Medium |
| 4 | Pre-seed devnodes: boot the master with all NIC models attached, let PnP install them, `BootFlags=1`, sysprep with `PersistAllDeviceInstalls` | Fixed slot and machine type; `HackFlags` 0x10000 for DSN NICs | Citrix PVS common image and CCBoot super client [production practice]; vmxnet3 online install + `Start=0` boots on the same VM [first-hand]; Microsoft warns against non-identical hardware [documented] | Medium |
| 5 | Multi-NIC iBFT at build time so Setup reflects and binds each NIC | Build VM with three NICs and three `sanhook`ed targets | iPXE emits one NIC record per NIC used to reach a target [working code]; Windows behaviour with several resolved NICs unknown | Low, one afternoon |
| 6 | Per-client pre-personalisation on the storage server (clone a devnode under the predicted instance ID at `New-Client`) | DSN formulas, a donor devnode per model, child mounted offline | Win7 recipe needed a real donor and failed when forged [first-hand, Win7]; DevePXEBoot V3 claims it, closed source | High |
| 7 | Edit the vendor INF (`StartType=0`, `BootFlags`) and re-add with `/ForceUnsigned` | Catalog breakage, test-signing | Does not change class-based boot-criticality [working code]; no success report; fights the April 2026 signer policy | Low, wrong layer |
| 8 | iSCSI HBA (physical) | Hardware | HBA is a storage controller; no iBFT or NIC driver involved [documented] | Purchase |

**Route 1 is Setup's own mechanism and should be run first.** The lab's `setupapi.offline.log` shows "Add Driver Package Offline", "Reflect Critical Driver Package" and "Add Service" for `net1ix64.inf` [lab], and the Win8-era documentation defines that operation as the file copy plus service creation [documented]; the OSR and Winclone evidence adds the `SYSTEM\DriverDatabase` subtree it writes (`DriverPackages\<pkg>\{Configurations\<cfg>\{Device,Services,Properties}, Descriptors\PCI\<hwid>, Strings}`, `DeviceIds\PCI\<hwid>` → inf, `DriverInfFiles\oemN.inf`) ([Twocanoes winclonefix logs](https://community.twocanoes.com/t/c-winclonefix-bat-command/5190); [OSR](https://community.osr.com/t/hklm-system-driverdatabase-driverpackages-bus-driver-inf-not-properly-configured/52214)) [shipping tool; first-hand]. Two things the current scripts should add. First, after the call, verify the three effects directly rather than trusting the return code: `<vol>\Windows\System32\drivers\netkvm.sys` (or `vmxnet3.sys`) exists; `ControlSet001\Services\netkvm` exists with `ImagePath`, `Group=NDIS`, `Start=3` and no `StartOverride` subkey; and `SYSTEM\DriverDatabase\DriverPackages\netkvm.inf_amd64_<hash>\Configurations` and `Descriptors` exist in the **SYSTEM** hive (load `config\SYSTEM`, not `config\DRIVERS`). `dism /Image:<vol> /Get-DriverInfo /Driver:<vol>\Windows\INF\oemN.inf` should then report `Boot Critical : Yes` [inferred from DISM's documented field]. Second, reflection of netkvm's or vmxnet3's INF yields a service without `BootFlags` because their INFs lack it, so `reg add ...\Services\<svc> /v BootFlags /t REG_DWORD /d 1` stays mandatory (both scripts do this). The server-side `critical` variant does not run `/Add-NetAdapter` and is therefore the cheaper test of whether reflection alone suffices; the WinPE `netadapter` variant is the complete emulation of Setup, with the real device as `/HostAdapter`. The one risk specific to virtio-net is the 2020 Setup failure at `SaveAdapterToOffline`; if `/Add-NetAdapter` fails after a successful reflection, boot anyway, because the kernel-generated binding path may not need it, and read the `netadapter.log`.

**Route 2 is the safe baseline and a diagnostic for route 1.** Microsoft's guidance has not changed since 2008 R2: install via Setup onto the LUN, then deploy "to other servers that use the same network adapter" ([About iSCSI Boot](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2008-R2-and-2008/ee619722(v=ws.10))) [documented], and the current overview adds only sysprep, differencing VHDs and iPXE ([iSCSI target boot overview](https://learn.microsoft.com/en-us/windows-server/storage/iscsi/iscsi-boot-overview)) [documented]. The lab's pipeline makes a new family a Terraform change to `dl-build-1`'s NIC model and one `build.sh` run. For vmxnet3 the 2026 Setup-install report predicts success [first-hand]; for virtio-net the outcome is unknown and informative either way: if Setup's `DeployIscsiDriversOffline` succeeds, `iscsi_boot_net.log` and `setupapi.offline.log` on the new image show exactly what a working netkvm reflection and binding look like, which is the template route 3 needs; if it fails with `0x80073b01`, the lab has reproduced the 2020 result on a matched build and can read the DISM log for the real cause. Check `Services\netkvm\BootFlags` on the finished image before first boot; if Setup did not set it, add it in `build.cmd` after `setup.exe /noreboot`.

**Route 3 is the fallback if drvstore refuses.** virt-v2v's exact Win8+ writes, verbatim from `inject_virtio_win.ml`, are: `DriverDatabase\DriverInfFiles\<inf>` with default `REG_MULTI_SZ [<label>]`, `Active REG_SZ <label>`, `Configurations REG_MULTI_SZ [<cfg>]`; `DriverDatabase\DeviceIds\PCI\<VEN&DEV&REV>` with a value named `<inf>` of `REG_BINARY 01 ff 00 00`; `DriverDatabase\DriverPackages\<label>\Version REG_BINARY` = `00 ff 09 00 00 00 00 00` + the class GUID in binary + 24 zero bytes ("necessary for Windows-Kernel-Pnp in w10/w2k16"); `...\Configurations\<cfg>` with `ConfigFlags REG_DWORD 0` and `Service REG_SZ <drv>`; `...\Descriptors\PCI\<id>` with `Configuration REG_SZ <cfg>`; and `Services\<drv>` with `Type 1`, `Start 0`, `Group`, `ErrorControl 1`, `ImagePath REG_EXPAND_SZ system32\drivers\<drv>.sys` ([inject_virtio_win.ml](https://github.com/libguestfs/libguestfs-common/blob/master/mlcustomize/inject_virtio_win.ml)) [working code]. The label must look like `<inf>_amd64_<16 hex>` or `pnputil /e` fails with `ERROR_INVALID_PARAMETER` ([libguestfs-common PR #17](https://github.com/libguestfs/libguestfs-common/pull/17)) [working code]; the `Version` trailer decodes as a FILETIME, four reversed `uint16` version fields and 8 zero bytes ([vrozenfe inject-public](https://github.com/vrozenfe/inject-public/blob/master/inject_driver.py)) [working code, independently cross-checked]. A Net-class port changes the class GUID bytes to `72 e9 36 4d 25 e3 ce 11 bf c1 08 00 2b e1 03 18`, uses `Group=NDIS`, adds `BootFlags=1`, and must supply the Net software-key AddReg (`Characteristics`, `BusType`, `*IfType`, `*MediaType`, `*PhysicalMediaType`, `Ndi\...`) in whatever `Configurations` subkey Windows uses, which no source confirms; the OSR fix worked by importing a real reflected `Configurations`/`Descriptors`/`Strings` subtree [first-hand], so export the golden image's `DriverPackages\net1ix64.inf_amd64_<hash>` subtree as the shape template and, better, the netkvm subtree from a route-2 virtio image if Setup produces one. Note that virt-v2v deliberately leaves NetKVM to PnP ("Block driver needs tweaks to allow booting; the rest is set up by PnP manager") [working code], and that Microsoft's own offline tooling "creates NO Services\netkvm key offline at all" ([inject-public](https://github.com/vrozenfe/inject-public/blob/master/inject_driver.py)) [working code, DISM capture], so this route has no Net-class precedent at all.

**Route 4 is the café and VDI industry's answer, and it works where instance IDs recur.** Citrix PVS's common image boots each disparate device once so Windows installs its drivers, then merges with `CIM.exe` and `regmodify.exe`, and insists the common NIC go "into the same slot" ([Citrix PVS 7.15 common image](https://docs.citrix.com/en-us/provisioning/7-15/managing-vdisks/vdisk-create/vdisks-common-image-create)) [production practice]; CCBoot's "super client" and "Collect Local NIC"/"Update image by PNP" do the same by hardware ID ([ccboot.com](https://www.ccboot.com/wikis-add-nic-drivers-to-image.htm)) [vendor docs]. For the lab: boot `golden-v<N>` on an e1000e VM that also carries a virtio-net at `net1` and a vmxnet3 at `net2`, let PnP install them, set `BootFlags=1` on `netkvm` and `vmxnet3ndis6`, and seal with `<PersistAllDeviceInstalls>true</PersistAllDeviceInstalls>` in `Microsoft-Windows-PnpSysprep`, which Microsoft allows only for "identical hardware ... connected to identical locations" ([PersistAllDeviceInstalls](https://learn.microsoft.com/en-us/windows-hardware/customize/desktop/unattend/microsoft-windows-pnpsysprep-persistalldeviceinstalls)) [documented]. Expect virtio-net clients to match when their NIC is at the same `netN` index and machine type (location hash), and vmxnet3 to miss (DSN) unless `HackFlags` is set first; an online-installed devnode does not need the kernel's `DriverDatabase` configuration because it already has `Service` and `ConfigFlags`, which is why the vmxnet3 `dd` image booted on its own VM [first-hand, inferred]. Also unbind the WFP LWF from any NIC installed online this way, since Setup protects only the install-time boot NIC ([KB2507616](https://learn.microsoft.com/en-us/troubleshoot/windows-server/performance/0x0000007b-stop-error-switch-alternate-iscsi-adapter)) [documented, Win7-era]; on Windows 11 `WFPLWFS` is itself `Start=0 BootFlags=1` [local check], so this is probably moot, but check the adapter's `FilterList`.

**Route 5 costs an afternoon and has no evidence.** iPXE's `ibft.c` writes one NIC record per network device actually used to reach a hooked target and one target record per session, pairing them by position ([ibft.c](https://github.com/ipxe/ipxe/blob/master/src/drivers/block/ibft.c); [commit 7cfdd76](https://github.com/ipxe/ipxe/commit/7cfdd76)) [working code]. A build VM with e1000e, virtio-net and vmxnet3, three LUNs each reached over its own NIC via `sanhook --drive 0x80/0x81/0x82`, with `set netX/gateway 0.0.0.0` on each, produces a three-NIC iBFT; the lab's `setupact.log` line `NICs in iBFT: N; NICs resolved: N` is the only instrument for what Setup does next. Caveats: the Initiator record takes the first session's IQN, every target must be reachable at each boot or the hook fails, the Linux kernel refuses more than two NIC or target records so iPXE's upstream testing stops at two [working code], and 2008 R2-era text says Setup special-cased one boot adapter for LWF binding [documented].

**Routes 6 and 7 are not worth the time now.** The Win7 Cyberus recipe (CDDB entry plus hardware key with `PreInstalled=1`, software key with `PreInstalled=1`, `BootNIC=1`, `Characteristics=0x84`, `BusType="5"`, service key with `ImagePath`) needed "a machine with the respective hardware" and "any attempt to forge the CDDB entry just from driver files has failed" ([Cyberus part 3](https://cyberus-technology.de/en/articles/windows-on-iscsi-part3/)) [first-hand, Win7]; Microsoft's Doron Holan: "The enum key is private to the os" ([OSR 47931](https://community.osr.com/t/how-to-boot-windows-7-over-iscsi-with-different-hardware/47931)) [Microsoft staff]. The Shunwang patent CN110618822B shows a production variant that pre-writes `Enum\PCI`, `Control\Class`, `Tcpip\Parameters\Interfaces` and `Control\Network` for the instance iPXE enumerated via UNDI, pointing at a stand-in service `iCafe8Net0` whose real binary is loaded from memory ([Google Patents](https://patents.google.com/patent/CN110618822B/zh)) [patent]; DevePXEBoot's V3 "builds the network card its own complete, correctly-identified adapter ... rewrites the device identifier" ([devepxeboot.devedse.click](https://devepxeboot.devedse.click/docs/plugins/auto-install-driver-plugin-v3)) [vendor claim, closed source]. Both confirm the target state but give no Windows 11 recipe. INF edits attack the service, not the configuration: `/ForceUnsigned` only waives the catalog check for offline staging ([DISM driver servicing](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/dism-driver-servicing-command-line-options-s14)) [documented], and nothing in Rapr's boot-critical resolution reads the service section [working code]. The one legitimate INF edit is adding `BootFlags = 1` (the 25398+ directive is available on 26100) to a package that something else will reflect, and the offline `reg add` achieves the same without breaking the catalog.

## Run the free checks first, then reflection, then Setup per family

The storage server can mount any child offline and the e1000e client already boots, so four checks cost nothing and shape everything after them. First, on the golden image (mounted read-only) load `Windows\System32\config\SYSTEM` and `config\DRIVERS` and record, for `net1ix64.inf_amd64_<hash>`, `netkvm.inf_amd64_<hash>` and `vmxnet3.inf_amd64_<hash>`, which hive holds `DriverDatabase\DriverPackages\<pkg>\Configurations`, whether `DeviceIds\PCI\VEN_1AF4&DEV_1041&SUBSYS_11001AF4&REV_01` (and `DEV_1000`) and `PCI\VEN_15AD&DEV_07B0` have values, and whether `ControlSet001\Services\{e1iexpress,netkvm,vmxnet3ndis6}` exist. The expected result, Intel in SYSTEM with a service and the other two only in DRIVERS without one, confirms the mechanism section's inferred SYSTEM-versus-DRIVERS placement [inferred, verifiable]. Also export the Intel package's whole `DriverPackages` subtree as route 3's template. Second, re-run the passing e1000e test with `--keep` and, on the client, read `Get-WinEvent -LogName Microsoft-Windows-Kernel-PnP/Configuration | ? Id -in 400,410,411` for the NIC (Driver Name, Driver Rank, "Device Updated"), `(Get-PnpDevice -Class Net).InstanceId`, `Get-NetAdapter | select InterfaceGuid`, and compare the GUID with `Services\Tcpip\Linkage\Bind` and `Control\Class\{4D36E972-E325-11CE-BFC1-08002BE10318}\000N\NetCfgInstanceId` in the golden image's offline hive. A new instance ID with event 400 "Device Updated: false" proves the kernel configured it at boot; a GUID that already appears in the image's `Linkage\Bind` means the kernel reused Setup's adapter object and route 1 needs `/Add-NetAdapter`; a fresh GUID means NDIS bound a kernel-minted adapter and reflection alone may suffice. Third, `Select-String BootFlags` over the pack's `netkvm.inf` and `vmxnet3.inf` to confirm the INFs lack it (expected, [local check]). Fourth, on the storage server, `Get-WinEvent -LogName 'Microsoft-Windows-iSCSITarget-Service/Admin'` around the failed virtio and vmxnet3 boots: events 20/21 only for iPXE's session and nothing from a Windows IQN [lab pattern] means Windows never reached the target, which already rules out "iSCSI login failed" for the current variants.

| Step | Action | Decides | If it passes | If it fails |
|---|---|---|---|---|
| 1 | The four offline/control checks above | Hive placement; whether `/Add-NetAdapter` is needed after reflection | Proceed with facts, not inferences | Revise the mechanism section before spending VM time |
| 2 | Fix `critical.ps1` (`0x180, 0x140`), add the same fallback and the three effect checks to `san/test-client.ps1`; run `nic-test.sh <v> dl-ws-3 critical` (vmxnet3, which has a Setup-install precedent) with the tap capture and serial KD from the next section armed | Whether force-reflection alone makes a staged Net package boot | Run on `dl-ws-1` (virtio); if both pass, route 1 is the design | Read the return code (Win32), `setupapi.offline.log` tail, and the three effect checks: no `Services\<svc>` means reflection did not happen (try 0x140, then the handle API); service present but `SYSTEM\DriverDatabase` lacking `Configurations` means a partial reflection (go to step 4) |
| 3 | `nic-test.sh <v> dl-ws-3 netadapter` (reflection + `BootFlags` + `/Add-NetAdapter` on the client) | Whether the TCP/IP binding was the missing piece | Route 1 with the WinPE step is the design; consider a server-side `/Add-NetAdapter` with a donor adapter later | If `/Add-NetAdapter` returns `0x80073b01`, boot anyway and capture; if 0x7B persists with a reflected service, the tap and `!devnode` split "device not started" from "no binding" |

Every step from 2 onward should run with the client's child BCD prepared for debugging and with a capture on the client's tap, because a bare pass/fail does not tell the two failure modes apart and the same instrumented run answers both.

## Diagnostics that tell the four failure modes apart

Serial KDCOM is the only debug transport that leaves the NIC under test alone. KDNET "takes exclusive control over the NIC it's configured to use. The OS doesn't load the native NDIS miniport for that NIC" ([KDNET manual setup](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/setting-up-a-network-debugging-connection)) [documented], and an OSR report shows exactly that producing 0x7B on a single-NIC iSCSI client, with the NIC's devnode in `CM_PROB_USED_BY_DEBUGGER` ([OSR](https://community.osr.com/t/is-kdnet-supported-with-iscsi-diskless-boot/57056)) [first-hand]; KDNET is usable only on a second e1000e (`8086:10D3` is on the supported list, Red Hat `1AF4` is not, [Supported NICs](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/supported-ethernet-nics-for-network-kernel-debugging-in-windows-11)) [documented]. On Proxmox, `qm set <VMID> -serial0 socket` creates `/var/run/qemu-server/<VMID>.serial0` ([Proxmox wiki, Serial Terminal](https://pve.proxmox.com/wiki/Serial_Terminal)) [documented]. The sourced bridge keeps WinDbg in a Windows VM on the same node, both VMs with `serial0: socket`, joined by `socat UNIX-CLIENT:/var/run/qemu-server/<client>.serial0 UNIX-CLIENT:/var/run/qemu-server/<debugger>.serial0` inside tmux, with WinDbg attached to COM1 at 115200 with Pipe unchecked and Reconnect checked ([Proxmox forum](https://forum.proxmox.com/goto/post?id=303322)) [first-hand, working]. This needs one long-lived SSH session, which suits the UniFi IPS constraint. Debugging from the PC is possible but untested: `args: -chardev socket,id=kdcom,host=127.0.0.1,port=4555,server=on,wait=off,nodelay=on -serial chardev:kdcom` on the VM (current QEMU spelling, [QEMU invocation](https://www.qemu.org/docs/master/system/invocation.html)) [documented], an `ssh -L 4555:127.0.0.1:4555` tunnel, `winsocat NPIPE-LISTEN:kd TCP:127.0.0.1:4555` ([winsocat](https://www.nuget.org/packages/winsocat)), then `windbg -k com:pipe,port=\\.\pipe\kd,resets=0,reconnect` ([VM COM port debugging](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/attaching-to-a-virtual-machine--kernel-mode-)) [documented syntax; chain untested]; never use `telnet=on`, which would mangle the binary KD protocol [inferred]. The client's BCD lives on its own EFI partition in the child, which the storage server mounts, so set it there before the boot:

```
bcdedit /store S:\EFI\Microsoft\Boot\BCD /set {default} debug on
bcdedit /store S:\EFI\Microsoft\Boot\BCD /set {dbgsettings} debugtype serial
bcdedit /store S:\EFI\Microsoft\Boot\BCD /set {dbgsettings} debugport 1
bcdedit /store S:\EFI\Microsoft\Boot\BCD /set {dbgsettings} baudrate 115200
bcdedit /store S:\EFI\Microsoft\Boot\BCD /set {default} bootdebug on
bcdedit /store S:\EFI\Microsoft\Boot\BCD /set {default} sos on
bcdedit /store S:\EFI\Microsoft\Boot\BCD /set {default} nocrashautoreboot on
bcdedit /store S:\EFI\Microsoft\Boot\BCD /set {default} bootstatuspolicy ignoreallfailures
bcdedit /store S:\EFI\Microsoft\Boot\BCD /set {default} bootmenupolicy legacy
bcdedit /store S:\EFI\Microsoft\Boot\BCD /set {default} testsigning on
bcdedit /store S:\EFI\Microsoft\Boot\BCD /set {default} nointegritychecks on
reg add "HKLM\<loaded SYSTEM>\ControlSet001\Control\Session Manager\Debug Print Filter" /v DEFAULT /t REG_DWORD /d 0xF
```

The element names and values are Microsoft's ([BCDEdit /set](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/bcdedit--set); [/dbgsettings](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/bcdedit--dbgsettings); [/bootdebug](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/bcdedit--bootdebug); [Debug Print Filter](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/reading-and-filtering-debugging-messages)) [documented]; setting `{dbgsettings}` elements through `/store` is untested, and `nointegritychecks` is only possible because Secure Boot is off. `bootlog yes` is useless here because `Ntbtlog.txt` lives on the volume that is inaccessible [inferred from the documented location]; `sos on` is the only in-box way to watch which boot drivers load without a debugger. With `/bootdebug on` winload breaks before it loads boot drivers, so the list it loads (does it include `netkvm.sys`?) is visible; with `windbg -d` the kernel breaks at the first module load, so `sxe ld netkvm` or `bp netkvm!DriverEntry` can be set before PnP runs [inferred from the documented options]. At the bugcheck, run `!analyze -v`; decode parameter 1 (`dt nt!_UNICODE_STRING <arg1>` if its first USHORT is even, `!devobj <arg1>` if it is 3, [Bug Check 0x7B](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/bug-check-0x7b--inaccessible-boot-device)) [documented]; then `lm m netkvm` (or `vmxnet3`), `lm m msiscsi`, `lm m ndis`, `lm m tcpip`; `!devnode 0 1 netkvm`, `!devnode 0 1 iScsiPrt`, `!devnode 0 1 pci`, `!devnode 0 0x21` (nodes with problems), `!devnode 0 0x11` (not started); `!drvobj netkvm 7`; `.reload /f ndis.sys`; `!ndiskd.netadapter`, then `!ndiskd.netadapter -handle <h> -state -bindings -log -ip`, `!ndiskd.protocols` ([!devnode](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/-devnode); [!ndiskd.netadapter](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/-ndiskd-netadapter)) [documented]. A healthy node reads `State = DeviceNodeStarted (0x308)`; the kernel-debugger evidence for a NIC that is loaded but not configured is `CM_PROB_NOT_CONFIGURED` and a stuck thread in `nt!PnpBootDeviceWait` ([OSR, winload.efi and drivers for booting](https://community.osr.com/t/winload-efi-and-drivers-for-booting/53801)) [first-hand]. `.dump /m` over serial is fine; a full dump at 115200 baud is not ([.dump](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/-dump--create-dump-file-)) [documented]. No `!iscsi` extension exists; the login phase is judged from the wire.

The wire capture is the single most informative instrument and needs no change to the client. The VM's NIC is `tap<VMID>i0` on the node ([apalrd, pcap tip](https://www.apalrd.net/posts/2023/tip_pcap/)) [first-hand]; run `tcpdump -i tap<VMID>i0 -nn -e -s 0 'arp or tcp port 3260 or udp port 67 or udp port 68' -w /root/<VMID>-boot.pcap` in the same tmux session before `vm_start`. On the Server 2025 target, `pktmon filter add -m <client MAC>`, `pktmon filter add -t TCP -p 3260`, `pktmon filter add -d ARP`, `pktmon start -c --comp nics -p 0`, then `pktmon stop` and `pktmon etl2pcap PktMon.etl --out boot.pcapng` ([pktmon filter add](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/pktmon-filter-add); [etl2pcap](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/pktmon-etl2pcap)) [documented]; `Get-WinEvent -LogName 'Microsoft-Windows-iSCSITarget-Service/Admin'` shows logon (20) and logoff (21) per the lab's own observations and a documented event 22 for "invalid iSCSI target" ([SCOM rule page](https://systemcenter.wiki/?GetElement=Microsoft.Windows.FileServices.Service.iSCSITarget.6.2.FailedLogin.InvalidTarget&Type=Rule&ManagementPack=Microsoft.Windows.FileServices.iSCSITarget.2012&Version=7.0.8560.0)) [third-party]. Capture the passing e1000e boot once as the template of a healthy phase B (Windows ARPs for 10.31.0.20, SYN to 3260, Login Request with the Windows IQN, full-feature reads).

The NTSTATUS mapping of Arg2 is community practice, not Microsoft documentation, which says parameters 2 through 4 are 0 ([Bug Check 0x7B](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/bug-check-0x7b--inaccessible-boot-device); [MS-ERREF](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-erref/596a1078-e883-4972-9bbc-49e60bebca55)) [documented values, inferred attribution]. The initiator's timers can be stretched to buy debugger time or shortened to iterate faster. Microsoft and NetApp place them under `HKLM\SYSTEM\CurrentControlSet\Control\Class\{4D36E97B-E325-11CE-BFC1-08002BE10318}\<instance>\Parameters` (`MaxRequestHoldTime` 60 s, `LinkDownTime` 15 s, `TCPConnectTime` 15 s, `DelayBetweenReconnect` 1 s, `MaxConnectionRetries` -1, `PortalRetryCount` 1, `NetworkReadyRetryCount` 10, `SRBTimeoutDelta` 15 s) ([timers quick reference](https://learn.microsoft.com/en-us/archive/blogs/san/microsoft-iscsi-software-initiator-and-isns-server-timers-quick-reference)) [documented, 2008]; TrueNAS uses `Services\iScsiPrt\Parameters` and warns a wrong location is silently accepted ([TrueNAS Hyper-V guide](https://cdn.truenas.com/docs/solutions/integrations/hyper-v/)) [vendor doc]; the 26100 binary's strings name `iscsiprt\parameters` with the boot-specific `WaitForNetworkAtBoot`, `DelayForNetworkAtBoot`, `NetworkReadyRetryCount`, `PortalRetryCount` and `BootConnectionPoolSize` [local check], whose defaults and units are undocumented. Write any experiment value to both keys and read it back; `MaxRequestHoldTime` 300 is the TrueNAS-recommended long setting. Finally, for the non-debugger path, the checks on a client's child after each variant are the registry facts that matter: `Services\<svc>` present with `ImagePath`, `Group`, `BootFlags=1`, no `StartOverride`; `SYSTEM\DriverDatabase\DriverPackages\<pkg>\{Configurations,Descriptors}` present; `DriverDatabase\DeviceIds\PCI\<hwid>` has a value named after the INF; `Control\Class\{4D36E972-...}\000N\NetCfgInstanceId` exists for the adapter and `Services\Tcpip\Linkage\Bind` lists `\Device\{that GUID}`; the adapter's `FilterList` carries no non-boot filter; `Control\Session Manager\Memory Management\PagingFiles` is whatever the e1000e control has; and `Control\PnP\Pci\HackFlags` is absent unless route 4 set it.

## Physical workstations shift the odds toward routes 1 and 2

On a Windows 11 26200 machine the inbox Net-class INFs that declare `BootFlags` 0x1 are Intel `net1ic64.inf` (`e1i68x64`, covering the 82574L `DEV_10D3`), Intel `net2ic68.inf` (`e2f68`, I225/I226), Realtek `rtcx21x64.inf` (`rtcx21`, RTL8125/8168 family), Realtek USB `rtucx21x64.inf`, the Mellanox `netmlx5.inf`/`netmlx4eth63.inf`/`mlx4_bus.inf`/`ipoib6x.inf` set, and Microsoft's own `iscsi.inf` for `iScsiPrt`; inbox `vmxnet3.inf` 1.8.17.0, Hyper-V `wnetvsc.inf`, Broadcom `b57nd60a.inf`, Killer, Marvell, Atheros and Realtek `rt640x64.inf` (inbox and vendor) do not [local check, 120 INFs scanned]. Intel's vendor `e1d68x64.inf` 12.19.1.37 sets it ([local check]); the lab's 82574L package does too [lab]. The split follows silicon with PXE/iSCSI option ROMs [inferred], and NiKiZe's rule of thumb that ISO releases "only work on NICs that have official iSCSI boot support" ([ipxe #1544](https://github.com/ipxe/ipxe/discussions/1544)) [first-hand] follows from it. Reports on 25H2 physical hardware: I219-V works with the in-box `e1d` driver and `StartType=3` ([ipxe #1544, imyzcn](https://github.com/ipxe/ipxe/discussions/1544)) [first-hand]; I226-LM on an ASUS WS680 failed with 0x7B despite `BootFlags=1`, `Start=0` and `/Add-NetAdapter`, while the same image booted an I219-V client ([ipxe #1544, colo808](https://github.com/ipxe/ipxe/discussions/1544)) [first-hand]; some onboard Realtek NICs refuse, Intel X710-DA2 is recommended, and a second onboard NIC left enabled cost one builder ten days ([ipxe #1544, ziks](https://github.com/ipxe/ipxe/discussions/1544#discussioncomment-15657892)) [first-hand]; Aquantia/Marvell 10 GbE "don't work at all" ([jakelmg/windows-diskless-boot](https://github.com/jakelmg/windows-diskless-boot)) [first-hand].

Three consequences follow for the lab's physical phase. Because Intel and most server NICs implement unique DSNs, every physical card is a new instance to the image, so route 4's pre-seeded devnode works only for boards whose NIC lacks a DSN or shares one (some Realtek parts, per an unverified forum snippet) and for `HackFlags`-modified images; the scalable path for mixed physical fleets is route 1, reflecting each family's package into one image, or route 2, one image per family with an iPXE or DHCP rule mapping `${net0/busid}` to the image. Because Windows Update replaced a Realtek driver under a new service name and dropped `BootFlags` ([ipxe #1544, EBADBEEF](https://github.com/ipxe/ipxe/discussions/1544#discussioncomment-15040865)) [first-hand] and Microsoft added `SPSVCINST_NOCLOBBER_BOOTFLAGS` only for re-installs of the same service ([INF AddService](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/inf-addservice-directive)) [documented], keep the lab's updates-off policy on clients and re-verify `Services\<svc>\BootFlags` in every new golden image. And because Setup only ever protected the install-time NIC from the WFP LWF ([KB976042](https://support.microsoft.com/en-us/topic/windows-may-fail-to-boot-from-an-iscsi-drive-if-networking-hardware-is-changed-5363d4bc-0103-e183-cb1c-8436e1691c13)) [documented, Win7-era] and a second NIC can crash the next boot (DevePXEBoot ships a tool that isolates every NIC except the booting one, [Common Issues](https://devepxeboot.devedse.click/docs/common-issues)) [vendor claim], disable or isolate non-boot NICs on physical clients during bring-up. If a truly NIC-agnostic physical image is ever required, only an iSCSI HBA delivers it: Microsoft states the HBA "is a true storage adapter" that "does not use the Microsoft iSCSI Software Initiator driver or an iBFT table" and can even be upgraded in place ([About iSCSI Boot](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2008-R2-and-2008/ee619722(v=ws.10))) [documented, 2008 R2]; NIC firmware initiators still hand over to the NDIS driver via the iBFT and share every problem above [documented].

## Conclusion

The question was never which flag to flip but which hive the kernel can read when it meets the NIC. Everything that failed in the lab (`BootFlags`, `Start=0`, a copied service, `/Add-NetAdapter`) edits things winload or NetSetup consume; the thing that worked for e1000e edits what the Phase-1 PnP configuration engine consumes, and only Setup's force-reflection ever wrote it. That reframing makes the lab's planned experiment the highest-value one, with one flag corrected and three offline effect checks added, and it makes the storage server, not WinPE, the natural place to do most of the work, since every registry fact that decides success is in a hive the server can mount. It also explains the field's two decades of folklore: the Windows 7 CDDB recipes, Citrix's same-slot rule and the café vendors' pre-boot registry writes are all ways of pre-creating what the kernel cannot create for itself.

Two things would change the picture. If the e1000e control shows a fresh `NetCfgInstanceId` bound without `/Add-NetAdapter`, then a reflected package is sufficient and the entire NIC problem reduces to running one undocumented drvstore call per driver family at image build time, which scales to physical fleets. If instead reflection succeeds but the kernel still leaves netkvm `CM_PROB_NOT_CONFIGURED`, the Net class is being filtered at boot by something DISM's `BootCritical` flag reflects and Setup's `Force` flag overrides, and the next place to look is the version-info `FORCE_BOOT_CRITICAL` bit and the `StatusFlags`/`ConfigurableFlags` properties of the reflected package, read back through `DriverStoreGetObjectPropertyW`. Either way the Server 2025 target and the 26100 image share a servicing stream, so pin the build, keep updates out of clients, and treat every new cumulative update as a fresh NIC test.
